# Plan: one container, and a first run that explains itself

Item 2 of the product review. Today a newcomer meets a 308 line compose file
with six services, a `/dev/snd` device mount that fails outright on a machine
with no sound card, 371 of the README's 601 lines about deployment, and then,
if they get that far, an empty app that does nothing until they find Settings
and paste an API key. The goal is that someone who has never seen Loreline can
run one command, open a page, and be recording, on a homelab box with no audio
hardware at all.

Two halves, built by two agents. They meet at one promise: the quickstart ends
with "open the page and it walks you through the rest", and the wizard is what
keeps that promise.

---

## Half A: zero to running

Owner: the deployment agent. Files: `docker-compose.yml`, `deploy/install.sh`,
`.env.example`, `README.md` (the Deployment section and everything above it),
`Dockerfile` only if it proves necessary.

**A1. The `/dev/snd` mount is the one thing that is actually broken.**
`docker-compose.yml` mounts `/dev/snd` into `app` unconditionally, so
`docker compose up -d` fails on a host with no sound card and on Docker Desktop
everywhere. `deploy/install.sh` already papers over it by writing a
`docker-compose.override.yml` that takes the mount away. **Invert that**: the
base file mounts no device, and the override that `install.sh` writes *adds*
the mount when the host has one. The default then works on every machine, and
the appliance keeps its microphone. `.gitignore` already ignores that override
file. Existing installs that have an override must keep working: read what
`install.sh` writes today before changing what it writes.

**A2. A quickstart that fits on one screen**, at the top of the deployment
material, before any of the appliance detail:

```
docker run -d --name loreline -p 8000:8000 -v loreline-data:/app/data \
  ghcr.io/luckytype/loreline:latest
```

Then `http://localhost:8000`, where the wizard takes over. Verify this actually
works before writing it down, including that the data volume survives a
`docker rm` and `docker run` again. Two things are worth saying next to it
because they are genuinely good news and not obvious: nothing needs a GPU or a
sound card, and **`localhost` is a secure context**, so on the machine you are
sitting at, "this device's microphone" works with no TLS setup at all. That is
the shortest honest path from nothing to a transcript, and it should be the
first thing a reader meets. Add the compose equivalent for people who prefer a
file, minimal, no more than a dozen lines.

**A3. Make the appliance-only settings overridable rather than baked.**
`LORELINE_DOCKER_API` points at the `docker-proxy` service and
`LORELINE_TRUSTED_PROXIES` at the bundled Caddy. In a one container run neither
service exists. Spell both as `${VAR:-<current value>}` so the effective
default does not change for anyone, and a minimal deployment can blank them
from `.env`. **Do not** move `caddy` or `docker-proxy` behind a compose
profile in this pass: a profile would mean the next `docker compose up -d` on
an existing install silently stops a running service. Note it as a follow up.

**A4. The README's shape is the deliverable, not just its content.** The
deployment section is longer than everything else put together, and a reader
deciding whether to try this has to wade through Bluetooth pairing and systemd
units to find out that it is one command. Lead with the quickstart, keep the
appliance install, the source install, updating and the Tailscale section, and
make the order match how a reader actually arrives. Do not delete material that
someone depends on; move it.

## Half B: a first run that explains itself

Owner: the wizard agent. Files: `src/loreline/web/auth.py`, a new
`src/loreline/web/routes/setup.py`, `src/loreline/settings.py`,
`frontend/src/routes/setup/`, `frontend/src/routes/+layout.svelte`,
`frontend/src/lib/api.ts`, tests, `docs/adr/0012-*.md`.

**B1. A password can be set from the browser, and is persisted.** Today
`settings.auth_password` comes from the environment only, and **an empty one
disables auth entirely** (`auth.py`, `auth_enabled`), so a bare `docker run` is
wide open on the network. That is acceptable for the seconds before setup and
unacceptable after, so the wizard's first step has to be able to close it.

Follow the precedent that is already in that file: `ensure_jwt_secret` mints a
secret on first boot and persists it in the `SecretStore`. Add the same shape
for the password: the environment wins when set, otherwise a stored value is
used, otherwise there is none and the app is in setup. Everything downstream
(`verify_password`, `_password_fingerprint`, the token's `pwd` claim) keeps
working unchanged, which also means setting a password immediately invalidates
nothing and logging in afterwards just works.

**B2. Setup state is a fact anyone may ask for.** `GET /api/setup/state`,
unauthenticated, returning only booleans: whether a password is configured,
whether any provider exists, and therefore whether setup is still open. It
reveals nothing an unconfigured instance is not already revealing by being
unconfigured.

**B3. The setup routes close behind themselves.** `POST /api/setup/password`
works only while no password is configured and answers 409 once one is, so the
endpoint cannot be used to change a password later. Changing it afterwards
stays what it is today: the environment, or a later feature nobody has asked
for yet.

**B4. The steps.** A `/setup` route in the SPA, rendered bare like `/login`:

1. **Set a password.** Explain in one line that the app is reachable by anyone
   on the network until this is done. Offer a generated suggestion.
2. **Add a provider.** One vendor, one key, with the existing Test button so
   the answer is known before the wizard closes. Reuse the provider wizard's
   own components rather than a second copy of that form. Skippable, because
   someone may want to look around first, but say plainly that nothing can be
   transcribed until a provider exists.
3. **How you will record.** Not a microphone picker: the honest question is
   which source this deployment will use. If the server has input devices,
   offer them. If it has none, say so and point at the browser, which is now a
   real answer. If the page is not in a secure context, say that the browser
   microphone needs HTTPS and link the Tailscale section rather than showing a
   dead control.

Finish on the dashboard.

**B5. The shell sends a fresh install to `/setup`, not `/login`.** The layout
already bounces a 401 to `/login` and carries a `next`. While setup is open,
that bounce goes to `/setup` instead. Once it is done, `/setup` answers that
there is nothing to do and sends the visitor on.

**B6. Say it out loud at startup.** One warning log when the app comes up with
no password configured, naming the URL to finish setup. An operator reading
`docker logs` should not have to infer that the instance is open.

**B7. The decision to record in the ADR.** First visitor completes setup, with
no token to copy from the logs. That is what Jellyfin, Home Assistant and
Nextcloud do, the window is seconds on a private network, and
`LORELINE_AUTH_PASSWORD` already exists for anyone who wants no window at all.
Write the reasoning down so it can be revisited rather than rediscovered, and
say what would change the answer (an instance published to the internet).

## Tests

- Setup state before and after a password, and after a provider.
- `POST /api/setup/password` succeeds once and 409s thereafter.
- The environment password wins over a stored one, and a stored one survives a
  restart.
- Auth is genuinely enforced after setup: a protected route that answered
  before the password now 401s without a cookie.
- The startup warning fires only when unprotected.
- The frontend has no test runner, so its half is covered by `npm run check`
  and the build.

## Out of scope, note as follow-ups

- Changing the password from Settings afterwards.
- Multiple users or roles. The single shared password is the model.
- Moving `caddy` and `docker-proxy` behind a compose profile.
- Importing an existing `.env` through the wizard.
